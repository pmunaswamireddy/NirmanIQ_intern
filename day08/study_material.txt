1. THE MENTAL MODEL: WHY NEXT.JS OVER PLAIN REACT?
================================================================================
When you build a React app with Vite or Create React App (CRA), you are building 
a Single Page Application (SPA).

Here is what happens in an SPA:
1. User visits `http://myapp.com/projects`.
2. Server responds with a blank HTML file containing only `<div id="root"></div>`.
3. The browser downloads a large JavaScript bundle (2MB - 5MB).
4. The browser parses and executes the JavaScript.
5. React mounts, runs `useEffect()`, makes a network call to fetch project data.
6. Finally, after 2 to 4 seconds, the user sees the page.

Why is this a problem on construction sites?
- Site engineers use low-end Android phones or rugged tablets with slow 4G/3G data.
- Waiting for huge JavaScript bundles leads to white screens and frustration.
- Search engines and social sharing bots see blank HTML, resulting in poor SEO.

How Next.js App Router Solves This:
Next.js renders your React components ON THE SERVER into ready-to-display HTML.
When a site engineer opens the link, the server immediately sends complete HTML.
The page is visible almost instantly (Fast First Contentful Paint).
Interactive buttons (like forms and dropdowns) then "hydrate" smoothly in the background.

Real-World Analogy:
- Plain React SPA = Buying raw ingredients from a grocery store and cooking at home.
- Next.js SSR = Ordering at a restaurant where the chef serves a hot, ready meal.

2. APP ROUTER ARCHITECTURE & SPECIAL FILE CONVENTIONS
================================================================================
Next.js uses file-system based routing inside the `app/` directory.
Every folder represents a URL path segment.

Special File Names & Their Roles:
--------------------------------------------------------------------------------
1. `page.tsx`
   - Defines the unique UI visible at that URL route.
   - Without a `page.tsx`, the folder cannot be visited as a web page.
   - Example: `app/projects/page.tsx` -> URL `/projects`.

2. `layout.tsx`
   - Wraps the current page and all child pages.
   - Does NOT re-render or lose state when navigating between child pages.
   - Ideal for headers, sidebars, footers, and persistent navigation menus.

3. `loading.tsx`
   - Automatically wraps the `page.tsx` in a React `<Suspense>` boundary.
   - Shows instantly while server data (e.g., database query) is being fetched.
   - Shows skeleton cards or spinners, preventing layout shifts.

4. `error.tsx`
   - Must be a Client Component (`'use client'`).
   - Catches runtime errors inside the page or its children without crashing
     the entire application.
   - Provides a `reset()` callback so the user can click "Try Again".

5. `not-found.tsx`
   - Displayed when `notFound()` is invoked or an invalid ID is requested.


Directory Tree Example:
```
app/
├── layout.tsx             # Root layout (Navbar, Footer, HTML shell)
├── page.tsx               # Homepage UI (/)
├── loading.tsx            # Global loading skeleton
├── error.tsx              # Global error boundary
└── projects/
    ├── page.tsx           # Projects list page (/projects)
    ├── loading.tsx        # Projects skeleton loader
    └── [id]/
        ├── page.tsx       # Project detail page (/projects/proj-101)
        └── towers/
            └── [towerId]/
                └── page.tsx # Tower detail page (/projects/1/towers/2)
```

3. SERVER COMPONENTS (RSC) VS CLIENT COMPONENTS ('use client')
================================================================================
This is the most critical concept in modern React.

Default Rule:
EVERY component inside the `app/` directory is a Server Component by default,
unless you explicitly write `'use client'` at the very top of the file.

Comparison Table:
--------------------------------------------------------------------------------
Feature                 Server Component (RSC)      Client Component ('use client')
----------------------  --------------------------  -------------------------------
Default in Next.js?     YES                         NO (Must add 'use client')
Where does it run?      Server only                 Server (SSR) + Browser
Bundle size impact      0 KB (Zero JS sent)         Added to client JS bundle
Can use useState?       NO                          YES
Can use useEffect?      NO                          YES
Can use onClick/events? NO                          YES
Can access window/DOM?  NO                          YES
Can fetch data direct?  YES (async/await DB/fetch)  YES (via useEffect / React Query)
Can read server env?    YES (process.env.SECRET)    NO (Only NEXT_PUBLIC_ variables)
--------------------------------------------------------------------------------

Beginner Mental Model:
- Use **Server Components** for 80% of your app: pages, layouts, data fetching,
  static cards, markdown rendering, footer text.
- Use **Client Components** ONLY for interactive "islands": modals, dropdowns,
  form inputs, search bars, toggle buttons.


Code Example — Server Component:
```tsx
// app/projects/page.tsx (Server Component - Default)
export default async function ProjectsPage() {
  // Direct async fetch on the server - no useState or useEffect needed!
  const res = await fetch('https://api.example.com/projects', { cache: 'no-store' });
  const projects = await res.json();

  return (
    <div>
      <h1>Construction Projects</h1>
      {projects.map(p => (
        <div key={p.id}>
          <h3>{p.name}</h3>
          <p>Status: {p.status}</p>
        </div>
      ))}
    </div>
  );
}
```

Code Example — Client Component:
```tsx
// components/CounterButton.tsx
'use client'; // <-- Required for interactivity

import { useState } from 'react';

export default function CounterButton() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}
```

4. DYNAMIC ROUTES & SEARCH PARAMETERS
================================================================================

A. Dynamic Routes (`[id]`):
When a URL segment varies dynamically (like an ID), use square brackets `[folderName]`.

Example: `app/projects/[id]/page.tsx`
In Next.js 15/16, route `params` are asynchronous Promises:

```tsx
interface PageProps {
  params: Promise<{ id: string }>;
}

export default async function ProjectDetailPage({ params }: PageProps) {
  const { id } = await params;
  return <h1>Project Details for ID: {id}</h1>;
}
```

B. Query Parameters (`?status=active`):
For filtering, pagination, or search terms, use query params.

Example: `http://localhost:3000/projects?status=active&sort=desc`
In Server Components:
```tsx
interface PageProps {
  searchParams: Promise<{ status?: string; sort?: string }>;
}

export default async function ProjectsListPage({ searchParams }: PageProps) {
  const { status, sort } = await searchParams;
  return <p>Filtering projects by: {status || 'ALL'}</p>;
}
```

In Client Components, use the `useSearchParams()` hook:
```tsx
'use client';
import { useSearchParams } from 'next/navigation';

export default function FilterDisplay() {
  const searchParams = useSearchParams();
  const status = searchParams.get('status');
  return <span>Selected filter: {status}</span>;
}
```

5. SHARED LAYOUTS, LOADING SKELETONS & ERROR BOUNDARIES
================================================================================

A. Shared Layouts (`layout.tsx`):
- Persists across route navigation.
- If a user clicks from `/projects` to `/projects/proj-101`, the sidebar does NOT
  unmount or re-render. Form inputs inside the sidebar keep their state.

B. Instant Loading Skeletons (`loading.tsx`):
- Next.js automatically streams `loading.tsx` to the browser while the server is
  executing async database or API operations in `page.tsx`.
- Prevents UI freezing and keeps the site feeling snappy.

C. Graceful Error Handling (`error.tsx`):
```tsx
'use client'; // Error boundaries MUST be Client Components

export default function ErrorBoundary({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div className="error-box">
      <h2>Something went wrong!</h2>
      <p>{error.message}</p>
      <button onClick={() => reset()}>Try Again</button>
    </div>
  );
}
```

6. BEGINNER PITFALLS & "INTERN WATCH-OUTS"
================================================================================
1. **Adding 'use client' everywhere**:
   - Pitfall: Marking every page with `'use client'` turns Next.js into a plain SPA,
     losing all SSR benefits.
   - Fix: Keep pages and layouts as Server Components. Only mark small interactive
     child components with `'use client'`.

2. **Async `params` in Next.js 15+**:
   - Pitfall: Writing `const { id } = props.params;` directly leads to runtime warnings.
   - Fix: Always await params: `const { id } = await props.params;`.

3. **Using `window` in Server Components**:
   - Pitfall: Trying to read `localStorage` or `window.innerWidth` in a Server Component
     causes `ReferenceError: window is not defined`.
   - Fix: Move browser-specific code into a Client Component inside `useEffect()`.

4. **Using `<a>` instead of `<Link>`**:
   - Pitfall: Using standard `<a href="/projects">` triggers a full-page browser refresh.
   - Fix: Always import and use `import Link from 'next/link'` for client-side navigation.

7. MEMORY HACKS & SUMMARY CHEAT SHEET
================================================================================
- **The "3-S" Rule of App Router:**
  - **S**erver by default (pages, layouts, data).
  - **S**plit interactive components to client islands.
  - **S**tream loading states with `loading.tsx`.

- **File Naming Mnemonic (P-L-L-E):**
  - **P**age: The view
  - **L**ayout: The shell
  - **L**oading: The skeleton
  - **E**rror: The safety net
