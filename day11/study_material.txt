1. THE MENTAL MODEL: WHY NESTJS OVER PLAIN EXPRESS?
================================================================================
If you have written backend code with plain Node.js Express or Python Flask, 
you probably wrote route handlers in one file, middleware in another, and database 
queries wherever you wanted.

Why this breaks down in large enterprise teams:
- **No Architectural Standard**: Every developer structures their files differently.
- **Tightly Coupled Code**: Routes directly call database queries, making unit testing impossible.
- **Spaghetti Middleware**: Logic becomes tangled as the codebase scales to hundreds of endpoints.

NestJS solves this by providing an opinionated, modular framework:
- Heavily inspired by Angular: TypeScript-first, decorators, and clean modular boundaries.
- Built on top of robust HTTP servers (Express by default, with Fastify option).
- Built-in Dependency Injection: Services are loosely coupled and trivially easy to mock and test.

Real-World Analogy:
- Plain Express = Building a house with loose bricks and whatever cement you find.
- NestJS = Constructing with prefabricated, engineered architectural beams where 
  electrical, plumbing, and structural modules clip cleanly together.

2. THE NESTJS ARCHITECTURE TRIANGLE
================================================================================
Every NestJS backend feature revolves around three fundamental concepts:

  Concept        Decorator       Role & Responsibility
  -------------  --------------  -----------------------------------------------
  1. MODULE      @Module()       The organizational boundary grouping related 
                                 controllers and providers (e.g., ProjectsModule).
  2. CONTROLLER  @Controller()   The traffic cop. Listens for HTTP requests,
                                 extracts parameters/body, and returns HTTP responses.
  3. PROVIDER    @Injectable()   The worker. Houses business logic, calculations,
     (SERVICE)                   and database access. Never deals directly with HTTP.


Visual Request Flow:
Client Request
      │
      ▼
┌──────────────┐
│  Controller  │  (Receives GET /projects, validates route params)
└──────┬───────┘
       │ delegates via DI
       ▼
┌──────────────┐
│   Service    │  (Fetches projects from memory/DB, filters, calculates risk)
└──────┬───────┘
       │ returns data
       ▼
┌──────────────┐
│  Controller  │  (Packages response into JSON and sends HTTP 200 OK)
└──────────────┘

3. DEPENDENCY INJECTION (DI) EXPLAINED FOR BEGINNERS
================================================================================
What is Dependency Injection?
Instead of a class creating its own dependencies with `new ProjectsService()`, 
the NestJS framework creates the instance for you and "injects" it into your constructor.

Why is this powerful?
1. Single Instance (Singleton): Only one copy of the service is created in memory, 
   saving RAM and sharing state across controllers.
2. Effortless Testing: When testing your controller, you can inject a mock fake service 
   without touching a real database.

Code Example:
```typescript
// 1. Mark the service as injectable
@Injectable()
export class ProjectsService {
  findAll() {
    return [{ id: 'proj-1', name: 'Skyline Hub' }];
  }
}

// 2. Inject it into the controller constructor
@Controller('projects')
export class ProjectsController {
  // NestJS automatically injects the singleton ProjectsService!
  constructor(private readonly projectsService: ProjectsService) {}

  @Get()
  getAll() {
    return this.projectsService.findAll();
  }
}
```

4. ROUTE DECORATORS & HTTP REQUEST LIFECYCLE
================================================================================
NestJS provides declarative decorators mapping directly to standard HTTP methods:

  HTTP Method  NestJS Decorator  Typical Purpose
  -----------  ----------------  -----------------------------------------------
  GET          @Get()            Retrieve resources (idempotent, safe)
  POST         @Post()           Create a new resource (returns 201 Created)
  PUT          @Put()            Replace/update an entire existing resource
  PATCH        @Patch()          Partially update fields of an existing resource
  DELETE       @Delete()         Remove a resource

Parameter Decorators:
- `@Param('id')`: Extracts URL route parameter (`/projects/:id` -> `id`).
- `@Body()`: Extracts the JSON payload from the request body.
- `@Query('status')`: Extracts URL query parameter (`/projects?status=ACTIVE`).
- `@HttpCode(201)`: Explicitly sets custom response status code.

CRUD Implementation Example:
```typescript
@Controller('projects')
export class ProjectsController {
  constructor(private readonly service: ProjectsService) {}

  @Get()
  getAll() { return this.service.findAll(); }

  @Get(':id')
  getOne(@Param('id') id: string) { return this.service.findById(id); }

  @Post()
  @HttpCode(HttpStatus.CREATED)
  create(@Body() body: any) { return this.service.create(body); }

  @Put(':id')
  update(@Param('id') id: string, @Body() body: any) { return this.service.update(id, body); }

  @Delete(':id')
  delete(@Param('id') id: string) { return this.service.delete(id); }
}
```

5. NESTED RESOURCE MODELING (/projects/:id/towers)
================================================================================
In construction domains, resources are hierarchical:
A Project contains multiple Towers; a Tower contains multiple Floors.

To represent this naturally in REST APIs:
- `GET /projects/:projectId/towers` -> Get all towers for that specific project.
- `POST /projects/:projectId/towers` -> Add a new tower into that specific project.

Controller Implementation:
```typescript
@Controller('projects/:projectId/towers')
export class TowersController {
  constructor(private readonly towersService: TowersService) {}

  @Get()
  getTowers(@Param('projectId') projectId: string) {
    return this.towersService.findByProject(projectId);
  }

  @Post()
  createTower(@Param('projectId') projectId: string, @Body() body: any) {
    return this.towersService.create(projectId, body);
  }
}
```

6. BEGINNER PITFALLS & "INTERN WATCH-OUTS"
================================================================================
1. **Forgetting to Add Service to Module `providers`**:
   - Pitfall: NestJS throws `Nest can't resolve dependencies of the ProjectsController`.
   - Fix: Check `projects.module.ts` and make sure `providers: [ProjectsService]` is listed!

2. **Putting Business Logic in Controllers**:
   - Pitfall: Writing database queries or math calculations inside `@Get()` functions.
   - Fix: Controllers must stay thin. Delegate all logic to your `@Injectable()` Service.

3. **Circular Dependencies**:
   - Pitfall: `ProjectsModule` imports `TowersModule` while `TowersModule` imports `ProjectsModule`.
   - Fix: Use `forwardRef(() => OtherModule)` or restructure shared logic into a common module.

7. MEMORY HACKS & SUMMARY CHEAT SHEET
================================================================================
- **The M-C-S Rule**:
  - **M**odule: Organizes the domain boundary
  - **C**ontroller: Routes the HTTP requests
  - **S**ervice: Executes the business logic

- **Controller Responsibilities**:
  - Accept request -> Call service -> Return response. (Never write business logic here!)

- **Postman Testing Tip**:
  - Verify `200 OK` for GET/PUT, `201 Created` for POST, and `404 Not Found` for missing IDs.
