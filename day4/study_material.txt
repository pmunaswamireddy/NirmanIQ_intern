1. TYPESCRIPT UTILITY TYPES IN DEPTH
================================================================================
Utility types are global generic helpers built into TypeScript. They take existing 
interfaces or types and transform them into new types without duplicating code.

--------------------------------------------------------------------------------
A. Partial<T>
--------------------------------------------------------------------------------
- What it does: Makes every property in type T optional by adding '?'.
- Why we need it: In HTTP PATCH endpoints, a client only submits fields that 
  need updating. You should never duplicate an interface just to make fields optional.
- Under the hood: { [P in keyof T]?: T[P] }

Example:
--------------------------------------------------------------------------------
interface Project {
  name: string;
  budget: number;
  city: string;
}

// Without Partial, you would have to write:
// interface UpdateProjectDto { name?: string; budget?: number; city?: string; }

type UpdateProjectDto = Partial<Project>;

const patchData: UpdateProjectDto = {
  budget: 75000000 // Only updating budget!
};

console.log("Partial update payload:", patchData);
--------------------------------------------------------------------------------
Terminal Output:
Partial update payload: { budget: 75000000 }

--------------------------------------------------------------------------------
B. Required<T>
--------------------------------------------------------------------------------
- What it does: Makes every property in type T strictly mandatory by removing '?'.
- Why we need it: If an interface defines optional fields for draft records, 
  Required<T> ensures an entity has every single field filled before publishing.

Example:
--------------------------------------------------------------------------------
interface SiteConfig {
  droneInspection?: boolean;
  maxDailyUploads?: number;
}

type StrictConfig = Required<SiteConfig>;

// Compile Error if any field is missing!
const config: StrictConfig = {
  droneInspection: true,
  maxDailyUploads: 100
};

console.log("Strict config:", config);
--------------------------------------------------------------------------------
Terminal Output:
Strict config: { droneInspection: true, maxDailyUploads: 100 }

--------------------------------------------------------------------------------
C. Pick<T, K> & Omit<T, K>
--------------------------------------------------------------------------------
- Pick<T, K>: Creates a new type selecting only the specified keys K.
- Omit<T, K>: Creates a new type removing the specified keys K.
- Why we need it: Prevents exposing sensitive internal fields (e.g., budget, 
  passwordHash) or omitting auto-generated fields (id, timestamps) on creation.

Example:
--------------------------------------------------------------------------------
interface TowerRecord {
  id: string;
  name: string;
  totalFloors: number;
  internalBudget: number; // Sensitive field
}

// 1. Pick: Choose only public display fields
type TowerCard = Pick<TowerRecord, 'name' | 'totalFloors'>;

// 2. Omit: Strip out internalBudget
type PublicTower = Omit<TowerRecord, 'internalBudget'>;

const card: TowerCard = { name: "Tower C", totalFloors: 18 };
const publicView: PublicTower = { id: "T-03", name: "Tower C", totalFloors: 18 };

console.log("Public Tower Card:", card);
console.log("Public Tower Record:", publicView);
--------------------------------------------------------------------------------
Terminal Output:
Public Tower Card: { name: 'Tower C', totalFloors: 18 }
Public Tower Record: { id: 'T-03', name: 'Tower C', totalFloors: 18 }

--------------------------------------------------------------------------------
D. Record<K, V>
--------------------------------------------------------------------------------
- What it does: Creates an object type where keys are of type K and values are of type V.
- Why we need it: Far safer than plain '{ [key: string]: any }' because it enforces 
  that every valid key from a union exists and maps strictly to type V.

Example:
--------------------------------------------------------------------------------
type TradeCategory = 'Civil' | 'Electrical' | 'Plumbing';

const workerCount: Record<TradeCategory, number> = {
  Civil: 45,
  Electrical: 12,
  Plumbing: 8
};

console.log("Worker Allocation:", workerCount);
console.log("Civil workers count:", workerCount.Civil);
--------------------------------------------------------------------------------
Terminal Output:
Worker Allocation: { Civil: 45, Electrical: 12, Plumbing: 8 }
Civil workers count: 45

--------------------------------------------------------------------------------
UTILITY TYPES QUICK REFERENCE TABLE:
--------------------------------------------------------------------------------
Utility Type    | What It Does                      | Real-World Use Case
----------------|-----------------------------------|--------------------------------------
Partial<T>      | Makes all properties optional     | HTTP PATCH update payloads
Required<T>     | Makes all properties mandatory    | Finalized database submissions
Pick<T, K>      | Selects specific keys K from T    | Lightweight summary cards / UI lists
Omit<T, K>      | Removes specific keys K from T    | Excluding sensitive internal fields
Record<K, V>    | Maps keys K to values of type V   | Lookup maps, lookup dictionaries

2. TYPE NARROWING & CUSTOM TYPE GUARDS (THE 'is' PREDICATE)
================================================================================
When data arrives from an external API, a database query, or user input, 
TypeScript does not know its exact runtime shape. Type narrowing is the process 
of refining a broad type (like a union or 'unknown') into a specific type.

Built-in Narrowing Mechanisms:
1. typeof: Checks primitive types ('string', 'number', 'boolean', 'function').
2. instanceof: Checks if an object is an instance of a specific class (e.g. Error).
3. in operator: Checks if a property key exists on an object ('budget' in data).

The Limitation of Built-in Guards:
Built-in checks cannot easily validate complex nested object shapes or discriminate 
between multiple API response contracts.

Custom Type Guards with 'is':
Syntax: function isTarget(arg: GeneralType): arg is SpecificType
Inside any 'if (isTarget(arg))' block, TypeScript guarantees 'arg' is of SpecificType!

Example: Handling Polymorphic API Responses
--------------------------------------------------------------------------------
interface SuccessResponse<T> {
  type: 'success';
  data: T;
  timestamp: string;
}

interface ErrorResponse {
  type: 'error';
  message: string;
  statusCode: number;
}

interface ValidationError {
  type: 'validation';
  fieldErrors: Record<string, string>;
}

type APIResponse<T> = SuccessResponse<T> | ErrorResponse | ValidationError;

// Custom Type Guard for Success
function isSuccess<T>(res: APIResponse<T>): res is SuccessResponse<T> {
  return res.type === 'success';
}

// Custom Type Guard for Error
function isError<T>(res: APIResponse<T>): res is ErrorResponse {
  return res.type === 'error';
}

// Custom Type Guard for Validation
function isValidationError<T>(res: APIResponse<T>): res is ValidationError {
  return res.type === 'validation';
}

// Safe Handler Function
function handleApiResponse<T>(res: APIResponse<T>): string {
  if (isSuccess(res)) {
    return `[SUCCESS] Data: ${JSON.stringify(res.data)}`;
  }
  if (isError(res)) {
    return `[ERROR ${res.statusCode}] ${res.message}`;
  }
  if (isValidationError(res)) {
    const fields = Object.keys(res.fieldErrors).join(", ");
    return `[VALIDATION FAILED] Invalid fields: ${fields}`;
  }
  return "Unknown response";
}

const res1: APIResponse<{ id: string }> = {
  type: 'success',
  data: { id: 'PRJ-101' },
  timestamp: '2026-10-03T10:00:00Z'
};

const res2: APIResponse<null> = {
  type: 'error',
  message: 'Database connection timeout',
  statusCode: 504
};

const res3: APIResponse<null> = {
  type: 'validation',
  fieldErrors: { budget: 'Budget must be greater than zero' }
};

console.log(handleApiResponse(res1));
console.log(handleApiResponse(res2));
console.log(handleApiResponse(res3));
--------------------------------------------------------------------------------
Terminal Output:
[SUCCESS] Data: {"id":"PRJ-101"}
[ERROR 504] Database connection timeout
[VALIDATION FAILED] Invalid fields: budget

3. ENUMS VS UNION LITERAL TYPES (THE NIRMANIQ RULE)
================================================================================
Many developers coming from Java, C#, or Python instinctively reach for 'enum'.
At NirmanIQ, TypeScript 'enum's are STRICTLY BANNED in favor of Union Literal Types.

Why NirmanIQ Mandates Union Literal Types:

1. ZERO RUNTIME FOOTPRINT (Zero Bundle Overhead):
   - Union literal types exist exclusively during compilation.
   - When TypeScript compiles to JavaScript, union literal types are completely erased.
   - Zero bytes of code are added to your production JavaScript bundle.

2. ENUMS GENERATE BLOATED RUNTIME JAVASCRIPT:
   TypeScript enums generate real JavaScript objects and IIFE closures:

   // TypeScript Enum:
   enum ProjectStatus {
     Planned,
     Active,
     Done
   }

   // Compiled JavaScript:
   var ProjectStatus;
   (function (ProjectStatus) {
       ProjectStatus[ProjectStatus["Planned"] = 0] = "Planned";
       ProjectStatus[ProjectStatus["Active"] = 1] = "Active";
       ProjectStatus[ProjectStatus["Done"] = 2] = "Done";
   })(ProjectStatus || (ProjectStatus = {}));

   This increases bundle size and creates subtle typing quirks.

3. THE NUMERIC ENUM PITFALL:
   Numeric enums are NOT type-safe. TypeScript allows assigning any arbitrary number 
   to a numeric enum variable:
   const s: ProjectStatus = 999; // Compiles without error! Very dangerous!

4. SEAMLESS JSON SERIALIZATION:
   When reading JSON from PostgreSQL, MongoDB, or an external REST API, the status 
   field comes across as a plain string: "in_progress".
   With union literals, it matches instantly: status === 'in_progress'.
   With enums, you have to write translation and parsing logic.

COMPARISON TABLE:
Feature             | TypeScript Enum                   | Union Literal Type (Mandated)
--------------------|-----------------------------------|--------------------------------------
Runtime Overhead    | Emits real JS objects & IIFEs     | Zero runtime code (completely erased)
Type Safety         | Numeric enums allow any number    | 100% strict compile-time guarantee
JSON Compatibility  | Requires mapping functions        | Direct 1:1 match with JSON strings
Tree-Shaking        | Resists tree-shaking              | Zero bundle size impact

Example:
--------------------------------------------------------------------------------
// NirmanIQ Standard Pattern:
type ProjectStatus = 'planned' | 'in_progress' | 'completed';

function getStatusBadge(status: ProjectStatus): string {
  switch (status) {
    case 'planned': return 'Badge: Blue (Planned)';
    case 'in_progress': return 'Badge: Amber (In Progress)';
    case 'completed': return 'Badge: Green (Completed)';
  }
}

console.log(getStatusBadge('in_progress'));
console.log(getStatusBadge('completed'));
--------------------------------------------------------------------------------
Terminal Output:
Badge: Amber (In Progress)
Badge: Green (Completed)

4. TSCONFIG.JSON STRICT OPTIONS EXPLAINED
================================================================================
The `tsconfig.json` file controls the TypeScript compiler (`tsc`). At NirmanIQ,
strict mode is mandatory to eliminate entire classes of production crashes.

Core Strict Options Under `"strict": true`:

1. `strictNullChecks`:
   - Without this flag, `null` and `undefined` can be assigned to ANY type.
   - With this flag, a `string` variable cannot be `null` unless explicitly typed:
     let name: string | null = null;
   - Eliminates the infamous "TypeError: Cannot read property of undefined".

2. `noImplicitAny`:
   - Flags an error whenever a variable or function parameter lacks a type annotation 
     and TypeScript cannot infer one.
   - Bad:   function calculate(x) { return x * 2; } // Error: 'x' implicitly has 'any' type
   - Fixed: function calculate(x: number): number { return x * 2; }

3. `strictFunctionTypes`:
   - Enforces strict variance checking on function arguments, preventing unsafe 
     function assignments.

4. `strictPropertyInitialization`:
   - Ensures that every class property is initialized either in its declaration 
     or inside the constructor.

5. `skipLibCheck`:
   - Skips type checking of external `.d.ts` declaration files inside node_modules.
   - Dramatically speeds up compile times while keeping your own codebase strictly typed.

6. `noEmit`:
   - Tells `tsc` to only validate types without generating `.js` files.
   - Perfect for modern toolchains where Vite, Next.js, or Node 22+ handles runtime execution.

Example: Demonstrating strictNullChecks Safety
--------------------------------------------------------------------------------
interface UserProfile {
  name: string;
  email?: string; // Optional (string | undefined)
}

function sendAlert(user: UserProfile): string {
  // If strictNullChecks is ON, user.email.toLowerCase() causes COMPILE ERROR!
  if (user.email) {
    return `Sending alert to: ${user.email.toLowerCase()}`;
  }
  return `No email available for: ${user.name}`;
}

const user1: UserProfile = { name: "Madhu", email: "Madhu@NirmanIQ.com" };
const user2: UserProfile = { name: "Suresh" };

console.log(sendAlert(user1));
console.log(sendAlert(user2));
--------------------------------------------------------------------------------
Terminal Output:
Sending alert to: madhu@nirmaniq.com
No email available for: Suresh

5. ESLINT & PRETTIER SETUP: CODE QUALITY AUTOMATION
================================================================================
In a team of dozens of developers, code quality cannot depend on manual vigilance:
- ESLint: Analyzes AST (Abstract Syntax Tree) to detect logical errors and anti-patterns.
- Prettier: Formats code automatically (indentation, semicolons, line length).

The 5 Most Common Lint Violations and How We Fix Them:

1. Use of 'var' (`no-var`):
   - Problem: 'var' is function-scoped and hoisted, causing subtle leakage bugs.
   - Bad:   var site = "Tower A";
   - Fixed: const site = "Tower A"; (or let if reassigned)

2. Banned 'any' (`@typescript-eslint/no-explicit-any`):
   - Problem: 'any' completely turns off type checking, defeating TypeScript's purpose.
   - Bad:   function parse(val: any) { ... }
   - Fixed: function parse(val: unknown) { ... } (forces narrowing before use)

3. Loose Equality (`eqeqeq`):
   - Problem: '==' performs implicit type coercion (`0 == ""` evaluates to true!).
   - Bad:   if (count == 0)
   - Fixed: if (count === 0)

4. Unused Variables (`@typescript-eslint/no-unused-vars`):
   - Problem: Clutters code, confuses reviewers, and often indicates unfinished logic.
   - Bad:   const tempScore = 95; // never used
   - Fixed: Remove variable, or prefix with underscore `_tempScore` if required by signature.

5. Empty Catch Blocks (`no-empty`):
   - Problem: Silently swallowing exceptions hides production outages.
   - Bad:   try { connect(); } catch (e) {}
   - Fixed: try { connect(); } catch (err) { console.error("Connection failed:", err); }

Example: Clean Code Adhering to All 5 Rules
--------------------------------------------------------------------------------
function safeCalculateRate(base: number, factor: number): number {
  // 1. Strict equality check
  if (factor === 0) {
    return 0;
  }
  
  // 2. Const declaration instead of var
  const rate = (base / factor) * 100;
  return Math.round(rate);
}

function parsePayload(input: unknown): string {
  // 3. Unknown instead of any with safe narrowing
  if (typeof input === 'string') {
    return input.trim();
  }
  return "default";
}

console.log("Calculated Rate:", safeCalculateRate(45, 90));
console.log("Parsed Payload:", parsePayload("   NirmanIQ Site   "));
--------------------------------------------------------------------------------
Terminal Output:
Calculated Rate: 50
Parsed Payload: NirmanIQ Site

6. COMPLETE ARCHITECTURAL EXAMPLE: CRUD DTO PATTERN
================================================================================
Below is the standard DTO architecture used across NirmanIQ microservices:

1. Base Interface: Defines the core business properties.
2. Create DTO: `Required<Base>` ensures no field is left blank during creation.
3. Update DTO: `Partial<Base>` allows patching any subset of fields.
4. Response Model: Extends Base with system-generated metadata (`id`, `createdAt`, `updatedAt`).

Example:
--------------------------------------------------------------------------------
// 1. Base Project Entity
interface ProjectBase {
  name: string;
  city: string;
  client: string;
  budget: number;
}

// 2. Create DTO (All fields mandatory)
type CreateProjectDto = Required<ProjectBase>;

// 3. Update DTO (All fields optional for PATCH)
type UpdateProjectDto = Partial<ProjectBase>;

// 4. Response Model (Includes system fields)
interface ProjectResponse extends ProjectBase {
  id: string;
  createdAt: Date;
  updatedAt: Date;
}

// In-Memory Repository
class ProjectRepository {
  private projects: ProjectResponse[] = [];

  create(dto: CreateProjectDto): ProjectResponse {
    const project: ProjectResponse = {
      ...dto,
      id: `PRJ-${this.projects.length + 1}`,
      createdAt: new Date(),
      updatedAt: new Date()
    };
    this.projects.push(project);
    return project;
  }

  update(id: string, patch: UpdateProjectDto): ProjectResponse | undefined {
    const item = this.projects.find(p => p.id === id);
    if (!item) return undefined;
    Object.assign(item, patch, { updatedAt: new Date() });
    return item;
  }

  list(): ProjectResponse[] {
    return this.projects;
  }
}

// Service Execution
const repo = new ProjectRepository();

const created = repo.create({
  name: "Godrej Woods",
  city: "Noida",
  client: "Godrej Properties",
  budget: 50000000
});

console.log("Created Project:", created.id, "-", created.name);

const updated = repo.update(created.id, { budget: 55000000 });
console.log("Updated Budget:", updated?.budget);
console.log("Total Projects in DB:", repo.list().length);
--------------------------------------------------------------------------------
Terminal Output:
Created Project: PRJ-1 - Godrej Woods
Updated Budget: 55000000
Total Projects in DB: 1
