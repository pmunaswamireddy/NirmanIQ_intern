2. THE DUAL-TOKEN AUTHENTICATION PATTERN
--------------------------------------------------------------------------------
A. Why Never Issue a Single 30-Day JWT?
If a single 30-day token is compromised (via XSS, network eavesdropping, or client
leakage), an attacker retains unrestricted access for an entire month with no
mechanism for revocation short of rotating global server signing keys.

B. The Production Architecture:
- Access Token (Short-lived, 1 hour):
  * Sent in the `Authorization: Bearer <token>` HTTP header with every request.
  * Verified statelessly by the API server using public/private or symmetric HMAC
    cryptography without querying PostgreSQL.
  * Ensures zero database bottlenecks for high-throughput endpoints.

- Refresh Token (Long-lived, 30 days):
  * Stored securely on client (httpOnly, Secure, SameSite cookie).
  * Stored as a salted bcrypt or SHA-256 hash in PostgreSQL (`users.refresh_token_hash`).
  * Presented only to `POST /auth/refresh` when the access token expires.

C. Refresh Token Rotation & Theft Detection:
1. User logs in -> Receives AT1 + RT1. Server stores hash(RT1).
2. AT1 expires after 1 hour. Client sends RT1 to /auth/refresh.
3. Server verifies hash(RT1) == users.refresh_token_hash.
4. Server generates AT2 + RT2, computes hash(RT2), and overwrites users.refresh_token_hash.
5. If an attacker attempts to replay RT1 later:
   * hash(RT1) != users.refresh_token_hash (which now holds RT2).
   * Server detects token theft or reuse anomaly.
   * Server immediately sets users.refresh_token_hash = NULL, revoking ALL active
     sessions for that user account across all devices.

4. NESTJS GUARDS: THE CANACTIVATE INTERFACE
--------------------------------------------------------------------------------
Guards determine whether a given request will be handled by the route handler.

Execution Lifecycle:
Client Request
      │
      ▼
Middleware (Logger, CORS, Rate Limit)
      │
      ▼
Guards (JwtAuthGuard -> RolesGuard)
      │
      ▼ (If canActivate() returns true)
Interceptors (Pre-controller)
      │
      ▼
Pipes (ValidationPipe, DTO Transforms)
      │
      ▼
Controller Action (e.g. createProject)
      │
      ▼
Interceptors (Post-controller / Response transform)
      │
      ▼
Exception Filters (If error thrown)
      │
      ▼
Client Response

A. JwtAuthGuard:
- Extends NestJS Passport AuthGuard('jwt').
- Extracts Authorization header Bearer token.
- Validates signature and exp timestamp.
- On error: Immediately throws HTTP 401 Unauthorized.
- On success: Attaches payload to `request.user`.

B. RolesGuard:
- Implements CanActivate.
- Uses Reflector to read @Roles() metadata from the handler and controller class.
- Verifies if `requiredRoles.includes(request.user.role)`.
- On mismatch: Throws HTTP 403 Forbidden.


5. CUSTOM PARAMETER DECORATOR: @CurrentUser()
--------------------------------------------------------------------------------
Instead of writing repetitive code inside controller methods:
```typescript
@Get('me')
getProfile(@Req() req) {
  const userId = req.user.userId;
  // ...
}
```

NirmanIQ uses a clean parameter decorator:
```typescript
export const CurrentUser = createParamDecorator(
  (data: keyof AuthenticatedUser | undefined, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest();
    const user: AuthenticatedUser = request.user;
    return data ? user?.[data] : user;
  },
);
```

Usage in Controller:
```typescript
@Get('projects')
findAll(@CurrentUser() user: AuthenticatedUser) { ... }

@Post('projects')
create(@Body() dto: CreateProjectDto, @CurrentUser('userId') userId: string) { ... }
```
