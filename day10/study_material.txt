1. THE MENTAL MODEL: SERVER STATE VS CLIENT STATE
================================================================================
Historically, developers attempted to store EVERYTHING in one massive global Redux
store: server data, user profiles, theme toggles, modal open/close states, and form inputs.

Why this failed in real enterprise applications:
- **Server State** does NOT belong to the client:
  - It lives in a remote PostgreSQL database.
  - Multiple users are mutating it simultaneously.
  - It can become stale at any millisecond.
  - It requires asynchronous loading states, error handling, retries, and deduplication.
- **Client State** is strictly local:
  - Synchronous UI state (is the sidebar open? what filter tab is selected? what is the auth token?).
  - Exists only inside the current user's browser session.

NirmanIQ Enterprise Golden Rule:
Never store API server responses in Redux or Zustand!
- Use **TanStack React Query** for all server cache and data fetching.
- Use **Zustand** exclusively for client-only UI state.

2. TANSTACK REACT QUERY FUNDAMENTALS
================================================================================
React Query is an asynchronous state orchestrator that handles caching, background
refetching, and stale-while-revalidate synchronization.

The Core Building Blocks:
1. `QueryClient`: The centralized cache manager storing data by query key.
2. `QueryClientProvider`: React Context wrapping your app so components can access the cache.
3. `useQuery`: The primary hook for declarative data retrieval.

Code Example:
```tsx
import { useQuery } from '@tanstack/react-query';

export function useProjects() {
  return useQuery({
    queryKey: ['projects'], // Cache identifier
    queryFn: async () => {
      const res = await fetch('/api/projects');
      if (!res.ok) throw new Error('Network error');
      return res.json();
    },
    staleTime: 1000 * 60 * 5, // Data is fresh for 5 minutes
  });
}
```

What React Query gives you automatically:
- **Request Deduplication**: If 5 components render on screen and all call `useProjects()`,
  React Query executes only ONE network fetch and shares the cached promise.
- **Window Focus Refetching**: When the site engineer switches back to the browser tab,
  React Query automatically checks if server data has changed.
- **Garbage Collection**: Unused cached data is cleanly removed from memory after a timeout.

3. MUTATIONS & OPTIMISTIC UI UPDATES (useMutation)
================================================================================
When creating, updating, or deleting data on the server, we use `useMutation`.

Optimistic Updates:
To make the application feel lightning-fast on 3G/4G networks, we can update the UI
IMMEDIATELY before the server confirms success. If the server fails, we roll back.

The 3-Step Optimistic Lifecycle:
```tsx
const createMutation = useMutation({
  mutationFn: (newProject) => fetch('/api/projects', {
    method: 'POST',
    body: JSON.stringify(newProject)
  }),

  // 1. onMutate: Runs BEFORE the network call
  onMutate: async (newProject) => {
    // Cancel any outgoing queries so they don't overwrite our optimistic update
    await queryClient.cancelQueries({ queryKey: ['projects'] });

    // Snapshot current cache state for rollback
    const previousProjects = queryClient.getQueryData(['projects']);

    // Optimistically update the UI cache
    queryClient.setQueryData(['projects'], (old = []) => [
      ...old,
      { ...newProject, id: 'temp-' + Date.now() }
    ]);

    // Return context containing previous state
    return { previousProjects };
  },

  // 2. onError: If network fails, roll back to snapshot!
  onError: (err, newProject, context) => {
    queryClient.setQueryData(['projects'], context.previousProjects);
  },

  // 3. onSettled: Always refetch to sync with real server ID
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ['projects'] });
  }
});
```

4. ZUSTAND: LIGHTWEIGHT CLIENT STATE MANAGEMENT
================================================================================
Zustand is a minimalistic, TypeScript-first state manager with zero boilerplate.
Unlike Redux, it requires no reducers, actions, dispatchers, or context providers.

Creating a Zustand Store:
```tsx
import { create } from 'zustand';
import { persist } from 'zustand/middleware';

interface UIState {
  sidebarOpen: boolean;
  selectedFilter: string;
  toggleSidebar: () => void;
  setFilter: (filter: string) => void;
}

export const useUIStore = create<UIState>()(
  persist(
    (set) => ({
      sidebarOpen: true,
      selectedFilter: 'ALL',
      toggleSidebar: () => set((state) => ({ sidebarOpen: !state.sidebarOpen })),
      setFilter: (filter) => set({ selectedFilter: filter }),
    }),
    { name: 'ui-storage' } // Persists directly to browser localStorage!
  )
);
```

Using Zustand inside any component:
```tsx
export function SidebarToggle() {
  const sidebarOpen = useUIStore((state) => state.sidebarOpen);
  const toggleSidebar = useUIStore((state) => state.toggleSidebar);

  return (
    <button onClick={toggleSidebar}>
      {sidebarOpen ? 'Collapse Sidebar' : 'Expand Sidebar'}
    </button>
  );
}
```

================================================================================

6. BEGINNER PITFALLS & "INTERN WATCH-OUTS"
================================================================================
1. **Mutating React Query Cache Directly**:
   - Pitfall: Writing `data.push(newProject)` corrupts the cache and skips re-renders.
   - Fix: Always use `queryClient.setQueryData()` or `queryClient.invalidateQueries()`.

2. **Selecting the Entire Store in Zustand**:
   - Pitfall: Writing `const store = useUIStore();` triggers re-renders whenever ANY
     unrelated property in the store changes.
   - Fix: Use selectors: `const sidebarOpen = useUIStore(s => s.sidebarOpen);`.

3. **Missing Query Key Dependencies**:
   - Pitfall: Using `queryKey: ['project']` for detail views forgets the dynamic ID.
   - Fix: Include variable parameters in the query key: `queryKey: ['project', id]`.

7. MEMORY HACKS & SUMMARY CHEAT SHEET
================================================================================
- **The State Separation Rule**:
  - Remote / Async / Database = **TanStack React Query**
  - Local / Synchronous / UI = **Zustand**

- **The Optimistic Update Mnemonic (M-E-S)**:
  - **M**utate: Update UI cache immediately (`onMutate`)
  - **E**rror: Roll back if request fails (`onError`)
  - **S**ettle: Invalidate and sync real server state (`onSettled`)
